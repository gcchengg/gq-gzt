# 履职建议独立模块设计

日期：2026-10-08

## 1. 目标与范围

把 `/boardGovernance/management/:directorId` 内的“意见建议”页签独立为“履职建议”，使董事或子企业董办发起建议、董办明确责任并下发、责任人落实及关闭都在同一条建议上完成。董事、综合管理部董办和对应任务负责人均能查看建议列表及办理过程。一汽股权角色首页在“履职任务管理”之后新增“履职建议落实”分组。

本次仅改 `boardGovernance` 演示工作台，延续根页面的本地 React 状态和现有模拟数据，不引入后端接口、持久化或新的登录体系。集团董办不参与这条子企业建议流程。

## 2. 已确认的产品规则

1. 董事发起时必须选择一项自己的已有履职任务，再填写建议内容；董事表单不要求填写责任部门、责任人或期限。
2. 子企业董办可直接发起，也可补充董事发起的建议。下发前必须明确责任部门、责任人和完成期限。
3. 责任人沿用“一汽股权”演示角色，在页面内按责任人筛选与办理，不增加独立角色。
4. 责任人提交落实结果后直接关闭任务，无董办验收或董事确认环节。
5. 同一前序履职任务允许关联多条建议。建议保留与任务的稳定 ID 关联及发起时的任务摘要。

## 3. 导航与页面

左侧“履职任务”作为可展开菜单，新增子项“履职建议”。董事和一汽股权角色均可看到此子项；集团董办菜单保持原有范围。

| 页面 | 地址 | 用途 |
|---|---|---|
| 履职建议列表 | `/boardGovernance/duty-suggestions` | 搜索、状态和责任人筛选，发起建议，查看各自可见的建议 |
| 履职建议详情抽屉 | `/boardGovernance/duty-suggestions/:id` | 保留列表作为背景，从右侧展开关联任务、建议内容、责任信息、落实结果、办理记录和当前角色可执行的动作 |

列表至少展示建议编号、建议摘要、提出董事、关联履职任务、责任部门、责任人、期限、当前状态及操作。点击建议后在列表上方打开详情抽屉；关闭抽屉返回列表并保留筛选条件。直接访问详情 URL 同样展示列表及已展开的抽屉；不存在的 ID 在抽屉内显示可返回列表的错误态。管理详情移除“意见建议”页签，在需要查看建议的上下文提供跳转链接，并带入董事筛选。原任务页中已隐藏的“意见建议落实”页签不恢复；旧 `?taskType=suggestion&bizId=...` 深链重定向到新详情，避免两套办理入口。

一汽股权首页在“履职任务管理”分组后新增“履职建议落实”，下方直接显示待办列表，不再设置二级 tab 或按部门拆分。列表行标明“综合管理部董办的任务”或“其他任务”：前者是“待董办补充”的建议，点击后在详情抽屉填写责任部门、责任人和完成期限并下发；后者是已下发且未关闭的责任人任务，点击后以指定责任人视角在抽屉办理。初始演示数据中两类任务各有一条。

## 4. 角色权限与可见范围

| 身份/视角 | 列表范围 | 可执行动作 |
|---|---|---|
| 董事 | 自己发起或与自己相关的建议 | 发起；查看后续补充、下发、落实和关闭记录 |
| 综合管理部董办（一汽股权角色） | 全部建议 | 发起；补充待下发建议的责任部门、责任人及期限；下发；查看全过程 |
| 对应任务负责人（一汽股权角色内按责任人筛选） | 分派给自己的建议 | 查看；保存落实进展；提交落实结果并关闭 |

当前工作台只有“一汽股权”这一子企业演示角色。页面提供董办全量视角与责任人筛选，操作按钮依据当前视角和建议的 `assignee` 判断，不把筛选器当作真实身份认证。若以后接入登录用户，权限判断应改用真实用户 ID，列表和详情需一致。

## 5. 数据与状态流转

继续使用 `BoardGovernancePage` 中的 `suggestionTasks` 作为唯一建议状态。每条建议至少包含 `id`、`directorName`、`sourceTaskId`、`sourceTaskSnapshot`、`content`、`initiatorRole`、`initiatorName`、`owner`、`assignee`、`deadline`、`handlingPlan`、`progress`、`result`、`feedback`、`files`、`status`、时间戳和按时间排序的办理记录。新建时保存前序任务 ID 与标题等摘要；后续任务内容变化不会抹去建议的原始来源。

| 状态 | 进入动作 | 下一步 |
|---|---|---|
| 待董办补充 | 董事提交建议；董办保存尚未分派的建议 | 董办补全责任信息并下发 |
| 待落实 | 董办完成责任部门、责任人、期限并下发 | 责任人保存进展或提交结果 |
| 办理中 | 责任人保存落实方案、进度或材料 | 继续保存或提交结果 |
| 已关闭 | 责任人提交落实结果 | 只读查看结果及全过程 |

董事发起表单只出现关联任务与建议内容；任务选项限定该董事可关联的已有履职任务，二者均必填。董办发起时还需选择董事、其前序任务并填写建议内容；可以先保存为“待董办补充”，也可以在责任部门、责任人、期限齐全时直接下发。无有效任务时给出空态和去履职任务的入口，不提交无来源建议。

责任人可分次保存落实方案、进度、反馈说明和佐证材料，保存进展不强制要求落实结果。点击“提交完成”时必须填写落实结果，系统将进度置为 100%，写入关闭时间和记录，状态变为“已关闭”。已关闭建议在本次流程中只读，不支持重新分派或重新打开。

原有模拟建议保留。能确定前序任务的记录补上 `sourceTaskId`；无法确定的记录保持原来源文字并标记为历史来源，可查看及完成原办理流程，但不能把它当作新建建议时的有效任务选项。新增建议一律满足关联规则。完成履职任务时若当前逻辑自动生成建议，应写入该任务 ID 和来源快照，并进入“待董办补充”，由董办分派，而非沿用任务负责人直接作为建议负责人。

## 6. 页面组件边界

- `DutySuggestionView` 负责列表、筛选、空态和详情路由展示，只通过回调修改根页面的建议状态。
- 建议表单负责按角色显示字段及校验；董办分派和责任人落实各自是独立表单，避免把所有字段强加给董事。
- 建议状态操作集中在根页面或纯函数中，统一创建、补充下发、保存进展和关闭时的状态及办理记录写入。
- 首页分组与管理详情仅消费建议数据并导航，不维护第二份建议记录。

这样可在不重写履职任务、报告与评价模块的前提下，让原有依赖 `suggestionTasks` 的完成数量和报告归集继续读取同一数据源。

## 7. 异常与验证

任务被删除或发生变化时，已有建议仍展示发起时的任务摘要；创建时只允许选择当前有效任务。未填建议内容或未选择任务不可提交；董办未补齐责任部门、责任人、期限不可下发；责任人未填落实结果不可关闭。没有权限的操作不显示或禁用，直接访问详情也遵守同一角色范围。

验证重点：菜单层级与路由；旧深链跳转；董事仅填写任务和建议；董办补充分派和直接发起；一汽股权首页待办分组顺序及跳转；责任人筛选与关闭；关闭后列表、首页和管理侧的状态一致；历史来源记录可读；无效任务与无效详情 ID 的提示。沿用项目现有前端测试和构建检查，不新增后端集成测试。
