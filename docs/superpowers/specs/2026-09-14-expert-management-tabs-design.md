# 专家人才库与入库管理合并设计

## 1. 背景与目标

当前专家人才库在侧边栏分别提供“专家人才库”和“入库管理”。前者维护已正式入库档案，后者办理推荐名单、邀请、核对、审批和聘书签署。两者是同一条人的前后两段，不是重复页面，但用户需要在两个一级菜单之间切换。

本次调整目标：

- 删除侧边栏“入库管理”菜单。
- 将“专家人才库”一级菜单改名为“专家管理”。
- 在 `/expertTalentList` 用两个一级 Tab 承载原两页内容。
- 业务只保留这一个地址。切换 Tab 只切换页面状态和渲染内容，不改 pathname、search 或 hash。
- 访问旧地址 `/expertTalentApplications` 时重定向到 `/expertTalentList`，并打开“入库办理”Tab。
- 办理流程、字段、审批、候选名单和在库档案 Drawer 都不改。
- 推荐名单、入库申请与在库档案仍是两套数据，不在本次打通一人一档。

## 2. 信息架构

调整后的专家人才库侧边栏保留：

1. 专家库看板
2. 专家管理
3. 调用管理
4. 运营管理

“入库管理”不再作为一级菜单。

页面地址只有 `/expertTalentList`，页面标题为“专家管理”。打开该地址时默认“在库专家”。

一级 Tab 是页面局部状态，不是路由。点击 Tab、点“邀请专家”只更新组件状态并切换渲染的工作区，地址栏始终保持 `/expertTalentList`。

旧地址 `/expertTalentApplications` 不再作为业务页面。访问时 `replace` 到 `/expertTalentList`，并通过 `location.state` 一次性打开“入库办理”。看板“处理待办 / 入库审核”、审批待办中的入库跳转改为进入 `/expertTalentList` 并带上该 state。刷新后 state 消失，回到默认“在库专家”。

侧边栏“专家管理”只指向 `/expertTalentList`。为避免旧地址在重定向前掉出专家菜单区，`isCompanyListArea` 可暂时继续识别 `/experttalentapplications`，但不为它保留菜单项或独立页面。

## 3. 页面结构

### 3.1 页头

页面标题为“专家管理”，副说明为“在库档案与入库办理分开管理”。标题旁的页面说明同时覆盖：

- 查询和续聘、解聘在库专家。
- 办理推荐名单、邀请、资料核对、审批、发送聘书和签署。

页头按钮跟随当前一级 Tab：

- 在库专家：沿用现有“导出”“邀请专家”。
- 入库办理：沿用现有“前往分管领导审批待办”“发起合作邀请”。

### 3.2 一级 Tab

标题下方提供两个一级 Tab：

1. **在库专家**：现有人才库状态条、搜索、领域筛选、表格和档案 Drawer。
2. **入库办理（N）**：N 为当前入库申请数。内容为现有入库管理主体，包括演示提示、阶段条，以及内部的“初始推荐名单 / 入库办理”子 Tab。

一级 Tab 套用现有入库页的子 Tab，不重排名单和申请列表。

### 3.3 Tab 内行为

在库专家 Tab 的筛选、分页、档案 Drawer、续聘和解聘保持不变。

入库办理 Tab 的邀请、申请表、核对、审批、发聘书、签署回调保持不变。

点“邀请专家”只切换到“入库办理”，并打开内部“初始推荐名单”子 Tab，不新做邀请流程。入库办理 Tab 内的“发起合作邀请”仍走现有邀请弹窗。

关闭 Drawer 或切一级 Tab 时，各自的筛选和滚动位置都保留。重新打开某一 Tab 时回到该 Tab 上次状态，不重置另一 Tab。刷新页面后一级 Tab 回到“在库专家”，因为地址不携带 Tab 信息。

## 4. 数据与状态

推荐名单、入库申请、在库专家继续分别读取现有 store 数据。签署完成生成在库档案的现有逻辑不变。

合并页维护以下状态：

- 当前一级 Tab，默认“在库专家”；仅当本次导航带有入库办理的 `location.state` 时初始为“入库办理”。
- 在库专家 Tab 的关键词、领域、状态筛选、选中档案和滚动位置。
- 入库办理 Tab 的阶段筛选、内部子 Tab、选中申请和滚动位置。

两套列表不合并、不去重、不改统计口径。

## 5. 空态与异常

各 Tab 继续使用现有空态、校验和演示提示。合并本身不新增空态文案。

若入库申请列表为空，“入库办理”Tab 仍显示，数量为 0。

## 6. 代码边界

用一个页面级容器组织标题和一级 Tab，例如 `ExpertManagement`。现有 `ExpertList` 与 `Enrollment` 改为可嵌入：嵌入时不再渲染各自的页面标题，只保留工作区。容器用 `useState` 切换两个工作区，不把 Tab 写入 URL。

`Enrollment` 增加受控或可初始化的内部子 Tab，供“邀请专家”打开“初始推荐名单”。不重构 CandidatePool、审批弹窗、聘书和签署逻辑。

本次只改与菜单合并直接相关的入口：

- `src/pages/expertTalent/index.jsx`：`/expertTalentList` 渲染合并页；`/expertTalentApplications` 重定向到合并页并打开入库办理。
- `src/pages/expertTalent/Enrollment.jsx`：支持嵌入和内部子 Tab 初始化。
- `src/components/AppShell.jsx`：菜单改名为“专家管理”并只指向 `/expertTalentList`，删除入库管理项。
- `src/pages/expertTalent/components/PageHelp/index.jsx`：新增“专家管理”说明，删除仅服务于旧一级菜单的独立条目或改为内部不再引用。
- 看板和审批待办中指向 `/expertTalentApplications` 的链接改为 `/expertTalentList`，并用 `location.state` 打开入库办理。

`src/routes.jsx` 继续注册 `expertTalentApplications`，仅用于重定向，不渲染独立页面。

不改调用管理、运营管理、看板分析区和专家小程序流程。

## 7. 验收标准

1. 侧边栏不再显示“入库管理”，原“专家人才库”显示为“专家管理”。
2. `/expertTalentList` 打开“专家管理”，默认“在库专家”。
3. 切换一级 Tab 时地址仍为 `/expertTalentList`，只切换渲染内容。
4. `/expertTalentApplications` 重定向到 `/expertTalentList` 并打开“入库办理”；刷新后回到“在库专家”。
5. 侧边栏“专家管理”始终高亮 `/expertTalentList`。
6. 在库专家的列表、筛选、档案 Drawer、续聘和解聘与合并前一致。
7. 入库办理的推荐名单、阶段条、申请列表、邀请、核对、审批、发聘书和签署与合并前一致。
8. 点“邀请专家”进入入库办理的“初始推荐名单”。
9. 看板、审批待办等现有链接仍能到达对应工作面。
10. 项目构建通过，其他专家库入口不受影响。

## 8. 测试范围

- 菜单与路由：旧菜单消失，业务地址只有 `/expertTalentList`，旧入库地址会重定向。
- Tab 切换：地址不变，数量角标、页头按钮和内部子 Tab 状态符合上述规则。
- 在库专家回归：筛选、查看档案、续聘、解聘。
- 入库办理回归：邀请、申请、核对、审批入口、发聘书。
- 邀请专家：从在库专家 Tab 切到推荐名单，不丢失入库页其他状态。
- 构建检查：无失效导入、未使用页面标题或旧菜单文案残留在侧边栏。
